# Sauda

Учёт товаров, касса и отчёты для розничных магазинов и площадка, где магазины заказывают товар у компаний —
производителей и дистрибьюторов. Один сайт на много магазинов и компаний: каждый видит только свои данные.

## Что есть

- **Товары**: список с категориями, фильтрами и поиском, карточка товара и услуги, генерация штрихкодов
  (в том числе весовых), импорт и экспорт Excel, быстрые товары для кассы.
- **Склад**: остатки по магазинам, критические и минусовые остатки, история движения товара.
- **Документы** с черновиками: приёмка от поставщика с оплатами, оприходование, списание, перемещение между
  магазинами, инвентаризация (выборочная и полная). Остатки меняет только проведение.
- **Касса** в браузере: смены, сканер штрихкодов, весовые этикетки, скидки, оплата наличными и картой, сдача,
  возврат по чеку, внесение и изъятие, печать чека.
- **Отчёты**: статистика продаж (по товарам, чекам, категориям, поставщикам, покупателям), смены, кассиры, скидки,
  прибыли и убытки, ABC-анализ, отменённые товары.
- **Управление**: сотрудники с ролями (владелец, менеджер, кассир), кассы, торговые точки, покупатели и поставщики.

- **Накладные с фото**: приложение [«Накладные в Sauda»](https://github.com/backwardzz/umag-ocr) распознаёт фото накладной
  и кнопкой «В Sauda» открывает страницу `/#/invoice`, где из строк создаётся черновик приёмки. Товары ищутся
  по штрихкоду, недостающие создаются. Данные передаются в адресе после `#` и на сервер не уходят.

- **Компании и заказы.** При регистрации выбирается «Магазин» или «Компания» (производитель, дистрибьютор, оптовая
  компания), город, телефон и реквизиты; кого из сотрудников пустить на сайт, компания решает сама.
  - **Профиль и филиалы.** У компании своя витрина (логотип, описание, условия доставки и оплаты, минимальный заказ)
    и филиалы по городам. Заказ магазина попадает в филиал его города, а если такого нет — в главный.
  - **Каталог: товар и его виды.** Товар («Coca-Cola») объединяет виды — фасовки со своим штрихкодом, ценой и остатком
    («0,5 л», «1 л»). Товар со всеми видами заводится в одном окне, штрихкод из общего каталога сам подставляет название
    и категорию, фото ищется по штрихкоду. Прайс из Excel раскладывается на товары и виды по размеру в названии.
  - **Склад.** Остаток ведётся по каждому виду в каждом филиале и правится прямо в таблице. Заказ магазина резервирует
    товар, отгрузка списывает его со склада; заказать можно не больше свободного остатка. В карточке товара — сколько
    продано, сколько осталось, кто покупает и история движения.
  - **Заказы.** Компания подтверждает заказ (может уменьшить количество или передать другому филиалу) и отгружает.
    Магазин видит цены компаний прямо в каталоге товаров и в пакетах «У меня новый магазин», собирает общую корзину
    (по заказу на компанию), одной кнопкой добавляет всё, что заканчивается, а отгруженный заказ принимает кнопкой
    «Принять товар» — создаётся черновик приёмки, недостающие товары заводятся сами.

Чек нефискальный: связи с ОФД нет.

## Запуск на своём компьютере

Нужны Node.js 22 (версия в `.nvmrc`) и запущенный Docker.

```bash
npm install
npm run setup      # всё сразу: база, .env.local, демо-данные и вход dev / admin1
npm run dev        # сайт на http://localhost:5181
```

То же по шагам:

```bash
npm run db:start   # локальная база Supabase в Docker, первый запуск скачивает образы
npm run seed       # демо-магазин с товарами и продажами за две недели
```

Скопируйте `.env.example` в `.env.local`; адрес и ключ локальной базы печатает `npx supabase status`.
Для `npm run seed` в `.env.local` нужны ещё `DEMO_EMAIL`, `DEMO_PASSWORD` и `SUPABASE_SERVICE_ROLE_KEY` —
под этой почтой и паролем потом входите на сайт. `npm run seed -- --fresh` пересоздаёт демо-магазин с нуля.

Сидер создаёт два входа с одним паролем: `demo@sauda.test` — магазин, `rep@sauda.test` — владелец
трёх компаний с филиалами в разных городах, каталогами (товары с видами), остатками и заказами в разных статусах.
`npm run seed:brands` добавляет к ним оптовую базу с ценами на товары пакетов «У меня новый магазин» (берёт их из
`samples/catalog.xlsx`) и компании известных марок, если для их товаров нашлись фото на белом фоне.

Для разработки сидер заводит ещё вход **логин `dev`, пароль `admin1`** (почта `dev@sauda.test`) — владелец
демо-магазина и всех демо-компаний. В поле «Почта или логин» логин без «@» превращается в `<логин>@sauda.test`.
Сидер работает только с локальной базой, поэтому в облаке такого входа нет.

### Своя база товаров

```bash
npm run import -- "C:путьк выгрузке.xlsx" --org "Название магазина" --city "Астана"
```

Загружает Excel с товарами в отдельный магазин демо-аккаунта (без аргументов — `samples/catalog.xlsx` в магазин
«Шалкар»; город нового магазина по умолчанию Алматы). Товар ищется по штрихкоду: повторный запуск с обновлённым файлом добавляет новые товары и обновляет
цены, названия, категории и поставщиков у существующих. Подходит выгрузка «Список товаров» из UMAG.
То же самое делает кнопка «Импорт / Экспорт → Импорт из Excel» на сайте. Папка `samples` в git не попадает.

### Общий каталог товаров

```bash
npm run catalog            # samples/catalog.xlsx → таблица catalog_products локальной базы
npm run catalog -- --dry   # только показать, что попадёт в каталог и в пакеты
```

Каталог (кнопка «Каталог товаров») общий для всех магазинов: название, штрихкод, единица и категория. Цен в нём нет:
цену, упаковку и наличие магазин видит из предложений компаний с тем же штрихкодом и заказывает прямо из каталога.
Берутся товары с заводским штрихкодом, внутренние коды магазина пропускаются. Пакеты мастера
«У меня новый магазин» собираются по правилам из `scripts/catalog-packs.ts` (ходовые марки по подкатегориям).
Пользователи каталог только читают, поэтому скрипту нужен служебный ключ. Для облачной базы:
`CATALOG_URL=https://<проект>.supabase.co CATALOG_SERVICE_KEY=<service_role> npm run catalog`.

## Проверки

```bash
npm test           # юнит-тесты и сквозной тест серверной логики на локальной базе
npm run e2e        # касса и страницы кабинета в браузере (Playwright, нужен npm run setup)
npm run lint       # ESLint: зависимости хуков, неиспользуемый код
npm run build      # проверка типов и сборка в dist/
```

Перед коммитом изменённые файлы проверяет ESLint (husky + lint-staged). Первый запуск Playwright:
`npx playwright install chromium`.

Сквозной тест и сидер работают только с локальной базой и отказываются запускаться на любой другой.

## Как устроено

- `supabase/migrations` — схема базы, права доступа (RLS) и серверные функции: продажа, возврат, смены,
  складские документы, импорт, отчёты, каталог и склад компании, заказы. Новую миграцию к локальной базе применяет
  `npx supabase migration up`, к облачной — `npx supabase db push`. Остатки и продажи меняются только через эти функции.
  После изменения схемы — `npm run db:types`: он обновляет `src/lib/database.types.ts`, по которым TypeScript проверяет
  имена таблиц, колонок и функций в запросах. CI сверяет этот файл с миграциями.
- Магазин и компания — это аккаунт в `orgs` (реквизиты, логотип). У магазина — торговые точки `stores` с городом,
  у компании — витрина `companies`, филиалы `company_branches`, товары `company_products` с видами `company_variants`,
  остатки `company_stock` и их история `company_stock_moves`. Города — справочник `cities`.
- `src/pages` — экраны кабинета и кассы, `src/ui` — общие компоненты, `src/lib` — работа с базой и расчёты.

## Выкладка в интернет

Сайт собирается и выкладывается на GitHub Pages сам при каждом пуше в `main` (`.github/workflows/pages.yml`).
Чтобы он работал у всех, ему нужна облачная база:

1. На [supabase.com](https://supabase.com) создать бесплатный проект, запомнить пароль базы.
2. На своём компьютере в папке проекта: `npx supabase login`, `npx supabase link` (выбрать проект)
   и `npx supabase db push` — миграции применятся к облачной базе.
3. В панели Supabase, Settings → API, взять Project URL и ключ `anon`. В репозитории на GitHub,
   Settings → Secrets and variables → Actions → Variables, создать переменные `VITE_SUPABASE_URL` и
   `VITE_SUPABASE_ANON_KEY` с этими значениями.
4. В панели Supabase, Authentication → URL Configuration, указать Site URL `https://backwardzz.github.io/sauda/` —
   на него ведут ссылки из писем.
5. Перезапустить сборку: Actions → Deploy to GitHub Pages → Run workflow.
6. Вход `dev` / `admin1` в облаке: во временном `.env.local` указать облачные `VITE_SUPABASE_URL` и
   `SUPABASE_SERVICE_ROLE_KEY` (ключ `service_role` из Settings → API, никому не передавать) и выполнить
   `npm run dev-user`. Пароль `admin1` слабый: для настоящих магазинов заведите отдельные входы.

В облачном проекте оставьте включённым подтверждение почты: приглашения сотрудников срабатывают только для
подтверждённого адреса.

## Регистрация и вход

- **Регистрация:** магазин, компания или сотрудник (по приглашению — без своей организации), имя, вид магазина,
  согласие с офертой и политикой (`#/terms`, `#/privacy`, тексты-черновики в `src/pages/Legal.tsx`;
  при их изменении поменяйте `TERMS_VERSION` в `src/pages/Auth.tsx` — согласие спросят заново), откуда узнали и промокод.
  Всё это хранится в `user_metadata` пользователя (Supabase → Authentication → Users).
- **Восстановление пароля:** «Забыли пароль?» → код из письма → новый пароль. В облаке в Authentication → Emails →
  Reset password вставьте шаблон `supabase/templates/recovery.html` (в нём код `{{ .Token }}`), тема:
  «Sauda: код для нового пароля {{ .Token }}».
- **Вход через Google** (кнопка скрыта, пока не настроено): в Google Cloud Console создать OAuth Client (Web),
  Authorized redirect URI — `https://<проект>.supabase.co/auth/v1/callback`; в Supabase → Authentication →
  Sign In / Providers → Google указать Client ID и Secret; в репозитории GitHub — переменная `VITE_GOOGLE_AUTH=1`.
  Согласие с офертой у вошедших через Google спрашивается на следующем шаге.

## Компания, филиалы и их кабинеты

Филиал компании — это и её склад в городе (`company_branches`). Сотрудник компании либо работает в головном офисе
(`org_members.branch_id` пуст), либо привязан к одному филиалу:

- **Головной офис** видит все филиалы и один меняет то, что относится к компании в целом: общий каталог товаров,
  филиалы и их зоны доставки, доступ магазинов к ценам, ключи API. Владелец компании всегда в головном офисе.
- **Сотрудник филиала** видит и ведёт только свой филиал: заказы, которые пришли в него, его остатки и их историю,
  свои цены и ассортимент, карточку филиала. Руководитель филиала (менеджер) сам приглашает и убирает сотрудников
  своего филиала. Общий каталог он видит, но не меняет; чужих филиалов, их заказов и остатков не видит.

Филиал подключается сам: при регистрации выбирает «Филиал компании», на следующем шаге находит компанию, выбирает
свой филиал из списка или описывает новый и отправляет заявку (`request_branch`). Владелец компании видит заявки
в профиле, в разделе «Заявки филиалов», и одобряет их (`decide_branch_request`): заявитель становится руководителем
выбранного филиала, а для нового филиал создаётся по данным заявки. Владелец может и сам привязать сотрудника к филиалу
или пригласить его сразу в филиал — в разделе «Сотрудники».

Ограничения проверяет база (RLS и функции), а не только интерфейс — см. раздел «Кабинеты филиалов» в `scripts/smoke.ts`.

## Демо без регистрации

Кнопка «Попробовать без регистрации» на странице входа: анонимный вход Supabase и свой демо-магазин посетителя
(`start_demo`: 24 товара, приёмки, продажи за 13 дней, открытая смена). Через 3 дня демо удаляется вместе
с анонимным пользователем (`app.cleanup_demo`, pg_cron раз в час). Из демо ничего не уходит наружу: заказы
компаниям, запросы прайса, приглашения и Webkassa запрещены, цены компаний не видны; анонимный вход не заводит
настоящий магазин или компанию.

В облаке: Authentication → Sign In / Providers → **Allow anonymous sign-ins** (и лучше капча — Turnstile,
переменная `VITE_TURNSTILE_SITE_KEY`, чтобы демо не создавали скриптом).

## Фискализация (Webkassa)

Sauda не касса: чеки фискализирует облачная касса [Webkassa](https://webkassa.kz), она же передаёт их в ОФД.
Магазин подключает свою кассу Webkassa в «Управление → Кассы»: заводской номер кассы, логин и пароль кассира
(пароль хранится в Supabase Vault, браузер его не видит), ставка НДС организации.

- Продажа, возврат, внесение и изъятие на такой кассе встают в очередь `fiscal_receipts`, серверная функция
  `supabase/functions/fiscal` отправляет их в Webkassa и записывает фискальный номер. Касса вызывает её после
  каждой операции; если Webkassa недоступна, продажа всё равно проведена, а чек уходит повторно.
- Смена закрывается только после того, как все чеки приняты и снят Z-отчёт (функция снимает его перед закрытием).
- Коды Webkassa (типы операций, оплат, НДС, единиц) — в `supabase/functions/fiscal/webkassa.ts`; их нужно сверить
  с документацией из кабинета интегратора Webkassa.

Локально, без доступа к Webkassa:

```bash
npm run fiscal:mock    # двойник Webkassa на :8788
npm run fiscal:serve   # функция fiscal; в supabase/functions/.env: WEBKASSA_URL=http://host.docker.internal:8788/api/
npm run fiscal:check   # сквозная проверка: продажа → чек в Webkassa → Z-отчёт → закрытие смены
```

Выкладка: миграция (`npx supabase db push`), затем `npx supabase functions deploy fiscal` и адрес Webkassa
`npx supabase secrets set WEBKASSA_URL=…` (без него функция ходит на тестовый стенд devkkm.webkassa.kz).

## Эксплуатация

Что происходит само (`.github/workflows`):

| Когда | Что | Файл |
| --- | --- | --- |
| Пул-реквест | типы, ESLint, юнит-тесты, `npm run setup`, сверка типов базы, сквозной тест, Playwright | `pages.yml` |
| Пул-реквест | предпросмотр сайта на Cloudflare Pages, ссылка комментарием | `preview.yml` |
| Пул-реквест, main, раз в неделю | поиск уязвимостей CodeQL | `codeql.yml` |
| Пуш в main | те же проверки → сборка → выкладка на GitHub Pages | `pages.yml` |
| После выкладки | релиз с тегом `vГГГГ.ММ.ДД.N` и списком влитых пул-реквестов | `release.yml` |
| Каждую ночь | резервная копия базы, проверка восстановлением, шифрование | `backup.yml` |
| Каждые 15 минут | доступность сайта, входа и базы; при сбое — issue «Сайт недоступен» | `uptime.yml` |
| Раз в неделю | пул-реквесты Dependabot с обновлениями npm и GitHub Actions | `dependabot.yml` |

Что настроить один раз (Settings репозитория на GitHub):

- **Резервные копии** — Environments → `backup`, секреты `SUPABASE_DB_URL` (строка Session pooler из
  supabase.com → Project → Connect, с паролем) и `BACKUP_PASSPHRASE` (храните отдельно: без него копию не
  расшифровать). Расшифровка скачанной копии: `gpg --decrypt sauda-ДАТА.tar.gz.gpg | tar xz`; восстановление —
  по [инструкции Supabase](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)
  файлами `roles.sql`, `schema.sql`, `data.sql`.
- **Ошибки в браузере** — Variables → `VITE_SENTRY_DSN` (sentry.io → проект React → Client Keys).
- **Предпросмотр** — Secrets → `CLOUDFLARE_API_TOKEN` (право Cloudflare Pages: Edit), `CLOUDFLARE_ACCOUNT_ID`,
  и проект Pages `sauda-preview` в Cloudflare.
- **Защита main** — Branches → правило для `main`: только через пул-реквест, обязательная проверка `test`.
- **Безопасность** — Code security: включить Dependabot alerts, Secret scanning и Push protection.
